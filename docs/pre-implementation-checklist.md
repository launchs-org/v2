# 実装着手前の確認項目

開発を始める前に決めておく項目の一覧。各項目の「回答」欄を埋めていく。
回答が決まったら `docs/endpoints/`・`docs/issues/` など該当箇所に反映し、経緯は `docs/talks/` に残す。

- 「候補」は Claude が挙げた選択肢のメモ(採用を決めたものではない)
- 「回答」はユーザーの原文。「決定」はそれを受けて Claude が整理した内容(違っていたら直す)
- 「未決」は追加の確認が必要な項目
- 決定済みで仕様書(`docs/endpoints/`・`docs/issues/`)へ未反映の項目は、末尾の「反映待ち一覧」にまとめてある

**回答:** 

**決定:** apply 中に変化するのは `deploy.status` だけで、`service.status` は変えない(コミット済みの仕様どおり)。`service.status`(pending / active / failed / deleting)は Service 自体の払い出し状態で、apply の進行は `deploy.status` が表す。サービス apply は再起動を伴うので(A-2)、`deploy.status` の `applying` が他の apply との排他ロックを兼ねる。

### A-2. サービスapplyの成功判定

**回答(追加):** `replicas: 0` のときは別の処理にして、別のステータスにすればよい。

**決定(追加):** `replicas: 0`(`scaled_zero`)の deploy に apply したときは、再起動する Pod が無いのですぐ完了する。完了後の `deploy.status` は `active` ではなく `scaled_zero` に戻す(config / service / mounts の3つの apply に共通)。

### B-3. ページング
一覧系(プロジェクト・build履歴・deploy履歴・ingress・volume)は現状「未設計」。初期リリースで必要か。
- 候補: 当面なし(全件) / limit+cursor / limit+offset

**回答:** ページングは必要ですね → 良さそうな方を採用して

**決定:** limit + cursor を採用。クエリは `limit` と `cursor`、レスポンスに `nextCursor`(最後なら `null`)を追加。履歴系は新しいものが次々に増えるため、offset だと重複・欠落が起きる。`limit` のデフォルト20・最大100は仮の値。

**回答:** 404かな

**決定:** 404 に統一。

### B-5. ID の形式

**回答:** uuidv4 でよくて 接頭辞も採用です

**決定:** 接頭辞 + UUID v4。

### B-6. 日時の形式とタイムゾーン
例は ISO8601 UTC (`2026-09-16T00:00:00Z`)。全APIでこれに統一でよいか。

**回答:** タイムゾーン日本向けでJTCにして 日付の表記は2026-09-16T00:00:00Z これでいいかな

**回答(追加):** JSTをベースにしましょう

**決定:** JST をベースにする。API が返す日時は `2026-09-16T09:00:00+09:00` の形にする(末尾の `Z` は UTC を表すので使わない)。仕様書の例にある `Z` 付きの日時は、反映時に直す。
**補足:** DB の列は `timestamptz` にして、アプリ側で JST に揃える想定。

### B-7. 名前(name)の制約

**決定:** `name` は英数字とハイフンで最大64文字。volume 名は project 内で一意。`userName` も英数字とハイフン。
**回答(追加):** 64文字とかにする?

**決定(追加):** `userName` も最大64文字。
**決定(仮):** `userName` は大文字小文字を区別せずに重複を判定する(`Alice` と `alice` は同じ名前)。project 名は同じユーザーの中で一意。

## C. 認証(別コンテナに切り出す)

### C-1. 認証コンテナの責務範囲
signup/login/refresh/me/logout を全部担当するか。ユーザーDBはどこに置くか。

**回答:** 全部担当します ユーザーDBはアプリのDBと同じデータベースインスタンスでデータベースだけ切り分ける

**決定:** 認証コンテナが5つとも担当。ユーザーDBはアプリと同じ PostgreSQL インスタンス内の別データベース。

### C-2. トークン検証の方式
サンプルのJWTは HS512。バックエンド(app)が検証するとき、共有シークレットで自前検証するか、認証コンテナに問い合わせるか。
- 候補: 共有シークレット(HS512) / 公開鍵(RS256/EdDSA) / 認証コンテナへ都度問い合わせ

**回答:** リフレッシュトークンは共有化ぎでアクセストークンは公開鍵検証にしたいね → JWKS 配信にしようかな

**決定:** access token は非対称署名。認証コンテナが JWKS を配信し、バックエンドは公開鍵を取得・キャッシュしてローカルで検証する。refresh token は認証コンテナだけが発行・検証するので、共有シークレットは不要。
**回答(追加):** EdDSA

**決定(追加):** 署名アルゴリズムは EdDSA(Ed25519)。

### C-3. トークンの有効期限
access token / refresh token / assetsToken(30分は確定済み)の期限。

**回答:** refreshtokenは自動更新にも対応したいけど1月とかでいいかもね アクセストークンは15分でいいとおもう → そうですね(ローテーションの意味で合っている)

**決定:** access token は15分、refresh token は約1か月。refresh のたびに新しい refresh token を発行し、古いものを無効化する(ローテーション)。`/refresh` のレスポンスは access token と新しい refresh token の両方になる。
**回答(追加):** それでいいんじゃない

**決定(追加):** 古い refresh token が再利用されたときは、盗用の疑いとして、そのユーザーの refresh token を全て失効させる。
**回答(追加):** 90日でいいかな

**決定(追加):** 絶対上限は90日。ローテーションを続けても、最初のログインから90日で再ログインが必要になる。

**回答(変更):** リフレッシュトークンは古いときに更新するでいい気はするけどリフレッシュトークンのリフレッシュいったんなしにするか そもそもリフレッシュトークンの有効期限を消すのもありかもしれん → まわしていいよ

**決定(変更):** 上のローテーションと、再利用の検知による全失効は取り下げる(ローテーションをしないので、再利用という状況がない)。refresh token は更新しない(いったんなし)。有効期限は固定で90日にする。access token は15分のまま。`/refresh` は access token だけを返し、signup・login・refresh のレスポンスの形は変えない。
**判断(私が選んだ):** 有効期限をなくす案もあったが、なくすと盗まれたときに止める手段がログアウトと BAN だけになるので、固定で90日を残した。期限は DB の jti の行で管理するので、あとからなくす・延ばすのは簡単。
**将来:** 「refresh token が古いときだけ新しいものを発行する」更新は将来対応。`/refresh` のレスポンスに `refreshToken` を足すだけで、今の形との互換を保てる。

### C-4. ログアウト・refresh の無効化管理
logout 済み refresh token をどこで管理するか(Redisは使わない方針)。refresh token のローテーションをするか。
- 候補: DBに jti を保存 / ローテーション有り / 無し

**回答:** リフレっっしゅトークンはデータベース直管理でいいんじゃないかな JTI で有効かどうかを管理する感じでいいとおもう  
アクセストークンは時間の管理だけでいいとおもう → そうですね

**決定:** refresh token は DB で jti を管理して有効・無効を判定する。access token は有効期限だけで、失効の管理はしない。そのためログアウトや BAN の後も、発行済みの access token は最大15分有効。auth/005 で未確定だった「ログアウト後の access token」はこれで決着。

### C-5. パスワード
ハッシュ方式(argon2id / bcrypt)、最小強度、サインアップの公開範囲(誰でも登録できるか招待制か)。

**回答:** argon2id にしましょう 最小強度はセキュリティに寄せる感じで 公開範囲は招待制でも公開でもいじれるようにしてほしい → そうしましょう(アカウント管理グループを作る)

**決定:** argon2id。サインアップは公開と招待制を設定で切り替えられるようにする。招待制には招待の仕組みが必要。
**回答(追加):** いいと思う

**決定(追加):** 最小強度は12文字以上。組み合わせ規則は課さず、よくあるパスワード・漏洩済みパスワードを拒否する。

### C-6. ログイン失敗のレート制限・ロック
(auth/002 で未確定として残している)

**回答:** レート制限はセキュリティにふって設ける形にするようにして アカウントのログインを制限やBANなどは認証基盤側でできるようにしたいですね → そうしましょう

**決定:** レート制限は安全側で設ける。アカウントのログイン制限・BAN は認証基盤側で行えるようにする(管理機能が必要)。
**回答(追加):** いったん適当に決めて

**決定(仮の値):**
- ユーザー名単位: 連続5回失敗で15分ロック。成功したらカウントをリセットする
- ロック中、パスワード誤り、存在しないユーザーは、全て同じ 401 を返す(アカウントの存在を推測されないため)
- IP 単位: ログイン試行は1分あたり20回まで。超えたら 429(`Retry-After` 付き)
- サインアップ: 同じ IP から1時間あたり10回まで。超えたら 429
- 値は設定で変えられるようにする
**補足:** ユーザー名単位のロックは、他人のアカウントをわざとロックさせる嫌がらせに使われうる。そのためロックは短め(15分)にし、IP 単位の制限も併用する。

## E. Temporal

**回答:** namespaceはそのままでキューは分けましょう

### E-2. Workflow ID の設計

**決定:** `{操作}-{リソースID}-{uuid}` のハイフン区切り(例: `apply-config-deploy-xxxxxxxx-…-{uuid}`)。

### E-3. リトライ・タイムアウトの標準値

**回答:** activity と workflow両方に置くべきだと思うんですよね

**決定:** Activity と Workflow の両方にタイムアウトを置く。具体値は実装時に決める。

### E-4. ビルドキャンセルの実装方式
Workflow への signal か、Workflow cancel か。「完了が先ならキャンセル不成立」をどう表現するか。

**回答:** これ要相談 → 採用で

**決定:** Temporal の cancel を使う。キャンセル要求が来たら、Workflow がビルド Activity にキャンセルを伝えて `canceled` を記録する。ビルドが先に完了していて Workflow が終了済みなら cancel が失敗するので、API が 409 に変換する。

### E-5. DBの status と Workflow の状態の同期
Activity が status を書き込む方針(確定済みの想定)で、Worker 障害時に status が `applying` のまま残る場合の復旧(再起動時の整合チェック等)をどうするか。

**回答:** 後処理でapplying を外して failed とかにする運用がいいと思うけど どう思う？ → それでいきましょう

**決定:** 二段構え。(1) Workflow が失敗・キャンセルされたときに、必ず `failed` にする補償 Activity を実行する。(2) 定期ジョブで、`applying` のまま期限を過ぎていて Workflow が実行中でない行を `failed` にする。

### E-6. Temporal の構築方法

### F-2. pending_* の保存形式
`pending_env` / `pending_mounts` / `pending_ports` / `pending_rules` / `pending_sizeMB` をカラム(JSONB)に持つか、別テーブルにするか。

**回答:** pending_って各テーブルの行に存在するんじゃないの？ → JSONB じゃなくて 列として持つんじゃないの？

**回答(追加):** 全部 pending_* の列を同じ形で持つ形

**決定(追加):** 全てのリソースで、現在値の列と `pending_*` の列を同じ形で、同じテーブルの行に持つ。数値・文字列は普通の列、配列・マップ(`env` / `args` / `ports` / `rules` / `mounts`)は JSONB の列にする。別テーブルには分けない。
**注意(この形の影響):**
- ボリュームの `mountedBy` の取得と、マウント中の削除の 409 判定は、deploy の `mounts` の JSONB を検索する形になる(GIN インデックスを付ける)
- service 削除時に、その service を参照する ingress の `rules` を消す処理は、アプリ(Workflow)側で JSONB を見て行う
- 外部キー制約では参照整合性を守れないので、アプリ側で守る。削除は Workflow で行う(F-3)ので、この形でも成り立つ

### F-3. 削除の方式

**決定:** 削除は Workflow で行う。最初に `deleting` 状態にしてロックする。いま `deleting` があるのは service だけなので、deploy / ingress / volume / project にも追加する。`deleting` 中の変更系操作は 409、GET は `deleting` を返し、削除が終わったら 404 になる。

### I-3. デプロイログの取得元
k8s の Pod ログ API を都度叩くだけか、ログ収集基盤(Loki 等)を入れるか。Pod 再作成後のログを残す必要があるか。

**回答:** ログ収集基盤は保守が増えるからなしで今回のシステムが直接とってくる設計でいいんじゃね サブスクライブして DBに流していく感じで監視用のコンテナをシステム側に用意する感じにしてそれが死んだら自動で切り替わるみたいなのは欲しいね → これはそうですね 設計しましょう

**決定:** ログ収集基盤は入れない。システム側にログ収集用のコンテナを用意し、Pod のログを購読して DB に保存する。収集コンテナが死んだら自動で別のものに切り替わるようにする。
**回答(追加):** 切り替えは ruft でいいんじゃね(Raft の意味として扱う)

**回答(追加):** Raftは採用です / I-3採用

**決定(追加):** 複数の収集コンテナで Raft によりリーダーを1つ選び、リーダーだけが Pod のログを購読して DB に書く。リーダーが死んだら、残りから新しいリーダーが選ばれて引き継ぐ。保持期間は H-3 のとおり7日。Raft の採用は確定(下の「注意」のコストを踏まえたうえでの決定)。
**注意:** Raft は奇数台(3台など)で動かし、ノードの発見と状態の永続化が必要になる。k8s 上では3台の StatefulSet にするのが現実的。重くなるようなら、k8s の Lease によるリーダー選出(`client-go` の `leaderelection`)に替える手もある。
**採用した提案:**
- 切り替えや再起動で欠落・重複が出ないよう、Pod ごとの読み取り位置を DB に保存する
- デプロイログ取得の仕様変更: 今は「再作成された Pod の古い `podId` は 404」としているが、DB に保存するので保持期間内は取得できるようにする。`pods` 配列は引き続き稼働中の Pod だけを返す
