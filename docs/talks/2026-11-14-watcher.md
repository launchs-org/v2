# 2026-11-14 watcher の導入(k8s の実際の状態を DB に反映する)

## きっかけ

deploy の `status` は、最後の操作(作成、反映、スケール)の結果しか表さない。`active` になったあとに Pod がクラッシュしても、DB は `active` のまま。`pods` は、API サーバーに k8s の権限を持たせない決めなので、常に空だった。ワーカーも、k8s に何度も問い合わせて起動を待っていた。

## 決めたこと(ユーザーの提案を、そのまま採用)

1. **k8s の実際の状態を DB に書くのは、watcher(新しいコンテナ)だけ**にする。
2. ワーカーの起動待ちは、**DB を読む形**に直す(別の PR)。watcher では、Pod の状態変化(クラッシュ、起動など)のログを残す。
3. **同時に1つだけ**動かすのは、Raft ではなく、**PostgreSQL の advisory lock**にする。DB はすでに中心にあり、開発の compose でも、本番でも、同じように動く。Raft は3台以上と永続化が要り、重い。k8s の Lease は、k8s に未接続の開発環境で試せない。
4. k8s のイベントを受け取って DB を更新する。**起動したとき(引き継いだときも同じ)は、先に全件を読み込み、DB との差分を反映**してから、受け取りに入る。

## 順序(PR を分ける)

1. watcher の土台(リーダー選出、観測、観測用のテーブル)。挙動は変えない。← 今回
2. `pods` の一覧を、DB から返す。
3. ワーカーの待機を、DB 読みにする。

## 注意として残したこと

- **ワーカーの待機を DB 読みにするとき**、watcher が止まると、起動が確認できず、300 秒で `failed` になる。また、k8s の更新の直後は、DB の観測値が古い設定のもの(すでに Ready)のことがある。更新後の generation を、待機の Activity へ渡して、`observed_generation` が追いつくまで待つ必要がある。
- watcher が status を書くかは、未決。いまは、観測値だけを書く。クラッシュで status を変えるかは、仕様に無い状態の扱いなので、別に決める。
- 利用者の deploy は、Datadog の自動計装の対象外にしてある(`admission.datadoghq.com/enabled: "false"`)。インフラ全体の監視は、Datadog のエージェント(DaemonSet)が続ける。
