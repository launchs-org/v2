# 2026-11-14 watcher の導入(k8s の実際の状態を DB に反映する)

## きっかけ

deploy の `status` は、最後の操作(作成、反映、スケール)の結果しか表さない。`active` になったあとに Pod がクラッシュしても、DB は `active` のまま。`pods` は、API サーバーに k8s の権限を持たせない決めなので、常に空だった。ワーカーも、k8s に何度も問い合わせて起動を待っていた。

## 決めたこと(ユーザーの提案を、そのまま採用)

1. **k8s の実際の状態を DB に書くのは、watcher(新しいコンテナ)だけ**にする。
2. ワーカーの起動待ちは、**DB を読む形**に直す(別の PR)。watcher では、Pod の状態変化(クラッシュ、起動など)のログを残す。
3. **同時に1つだけ**動かすのは、Raft ではなく、**PostgreSQL の advisory lock**にする。DB はすでに中心にあり、開発の compose でも、本番でも、同じように動く。Raft は3台以上と永続化が要り、重い。k8s の Lease は、k8s に未接続の開発環境で試せない。
4. k8s のイベントを受け取って DB を更新する。**起動したとき(引き継いだときも同じ)は、先に全件を読み込み、DB との差分を反映**してから、受け取りに入る。

## 順序(PR を分ける)

1. watcher の土台(リーダー選出、観測、観測用のテーブル)。挙動は変えない。← 今回
2. `pods` の一覧を、DB から返す。
3. ワーカーの待機を、DB 読みにする。

## 注意として残したこと

- **ワーカーの待機を DB 読みにするとき**、watcher が止まると、起動が確認できず、300 秒で `failed` になる。また、k8s の更新の直後は、DB の観測値が古い設定のもの(すでに Ready)のことがある。更新後の generation を、待機の Activity へ渡して、`observed_generation` が追いつくまで待つ必要がある。
- watcher が status を書くかは、未決。いまは、観測値だけを書く。クラッシュで status を変えるかは、仕様に無い状態の扱いなので、別に決める。
- 利用者の deploy は、Datadog の自動計装の対象外にしてある(`admission.datadoghq.com/enabled: "false"`)。インフラ全体の監視は、Datadog のエージェント(DaemonSet)が続ける。

## 追記: 保存期間とクラッシュの上限(同日)

- **イベントの保存期間**: 30 日。あわせて、1つの deploy につき 1000 件(新しい順)。削除は、リーダーの watcher が1時間ごとに行う(書き手は watcher だけ、という決まりのため)。
- **クラッシュし続ける Pod の上限**: 上限を超えたら、**Deployment のレプリカを 0 にして再試行を止める**(採用)。DB の `replicas`(希望する数)は変えず、`status` を `failed` にし、`crash_loop_limit` のイベントを残す。`failed` の deploy は、同じ数でスケールし直せる。
  - 上限の値(仮): 同じ Pod が CrashLoopBackOff のまま 30 分続く、または再起動が 20 回に達する。→ **下の追記で、10 分に変更**。
  - 対象外: `applying`、`pending`、`deleting` の間(作成と反映には、300 秒の期限がある)。
  - 実装は、ワーカーの待機を DB 読みにしたあと(Workflow で止める)。
- **コンテナの出力ログ**(アプリの標準出力)は、watcher には入れず、別コンテナの **logcollector** にする。理由: ストリームを Pod の数だけつなぐ重い処理で、状態の反映を遅らせないため。権限(`pods/log`)も分けられる。どの Pod を追うかは、watcher が書く `deploy_pods` から分かる。

## 追記: ワーカーの起動待ちを DB 読みにした(3/3)

- watcher が止まったときは、**k8s に直接問い合わせる**(採用)。待ち続けて 300 秒で failed にすると、watcher の障害で、正常な deploy が failed になるため。
- 「watcher が生きているか」は、観測値の `observed_at` では分からない(安定している deploy は、イベントが無く、更新されない)。そこで、リーダーの watcher が 10 秒ごとに書く**心拍**(`watcher_heartbeats`)を使い、30 秒以上古ければ、止まっているとみなす。時刻は DB の時計だけで比べる。
- 更新の直後に、古い設定の観測値(すでに Ready)を信用しないよう、更新の Activity が Deployment の **generation を返し、待機に渡す**。観測値の generation がそれ以上になるまで待つ。
- 実機(Talos)で、DB で判断(2.4 秒で active)、更新直後に新しい設定の Pod が動いていること、watcher を止めて 35 秒後に作成すると k8s の直接確認で active、watcher を戻すと DB に戻ること、を確認した。

## 追記: クラッシュの上限は、猶予 10 分の時間だけにした(2026-11-15)

- 「CrashLoopBackOff になった瞬間に止めればよいのでは」という提案を検討した。**簡単になるが、CrashLoopBackOff は最初の数回のクラッシュ(約 1 分)で出る**ため、依存先(DB など)が短く止まっただけで、全部の deploy が `failed` になり、利用者が 1 つずつ手でスケールし直すことになる。k8s のバックオフは、一時的な失敗を乗り越えるための仕組みなので、**猶予を置く**ことにした。
- 猶予は **10 分**(30 分は、利用者から見て、`active` のまま壊れて見える時間が長い)。k8s の再起動の間隔は最大 5 分まで延びるので、10 分で、およそ 6〜7 回の再起動になる。
- **「再起動 N 回」の条件は、やめた。** `restart_count` は累積で、何日も安定して動いた Pod が一度のクラッシュで止まる危険がある。また、再起動の間隔が延びるため、10 回に達するのは約 20 分後で、時間の条件が先に満たされる。環境変数も、`CRASH_LOOP_UNHEALTHY_FOR`(既定 10m)だけになった。
