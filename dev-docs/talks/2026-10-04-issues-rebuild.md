# 2026-10-04 Issues再構築・エンドポイント分割

## 背景・経緯

- `dev-docs/endpoints.md` と `issues/` 配下にエンドポイント仕様とレビュー用Issueをまとめていたが、両方とも1ファイル/フラット構成でボリュームが大きくなりすぎた。
- 一旦 Issues を全部消し、コミット履歴もいったん整理した上で、詳細設計レビューを最初からやり直すことにした。

## やったこと

1. **コミット履歴の整理**
   - `develop` を `92877bb`(readme.md追加)まで `git reset --hard`。
   - `dev-docs/endpoints.md` の最新内容のみ新規コミットとして積み直し。
   - `origin/develop` に対して force push し、過去のIssue関連コミットを履歴から除去。

2. **`dev-docs/endpoints.md` の分割**
   - 1ファイルが大きくなりすぎたため、`dev-docs/endpoints/` ディレクトリを作成。
   - グループ(認証/プロジェクト/ビルド/デプロイ/サービス/イングレス/ボリューム)ごとにファイルを分割し、`README.md` を索引にした。

3. **`dev-docs/issues/` の再構築**
   - `issues/` を `dev-docs/issues/` に移動(ドキュメント類を `dev-docs/` 配下に集約)。
   - `dev-docs/endpoints/` と同じグループ単位でサブディレクトリを作成する方針に変更。
   - **レビューは1グループずつ進める**方針を確立(ユーザー指示)。`dev-docs/issues/README.md` にグループごとのレビュー進捗チェックリストを設置。
   - 各グループは `README.md`(Issue一覧)+ 連番の個別Issue(`001-xxx.md`)で構成。個別Issueのフォーマット: カテゴリ/Method・Path → 説明 → テスト要件(正常系/異常系/境界値)→ 仕様(JSON例)→ 参照。

4. **レビューで確定した仕様(ビルド関連)**
   - アップロード: zipの拡張子/Content-Type偽装や、パストラバーサルを含む不正ファイルは拒否する。
   - ビルド: `buildTargetDirectory` 不在や `repoUrl`/`ref` 不正について、専用の事前検証は設けない。実際のビルド処理で対象が見つからず自然に `status: "failed"` になるだけで十分、という方針に整理(事前バリデーションを過剰に作り込まない)。
   - ビルドキャンセル: `canceling` に遷移した後、中断処理より先にビルドが自然に完了した場合はキャンセルが不成立になり、先に確定した `success`/`failed` が優先される。
   - ビルドログ取得: `since` が現在のログ末尾を超える値の場合はエラーにせず、空ログ + 現在の `nextSince` を返す。

5. **`CLAUDE.md` の新規作成**
   - ディレクトリ構成、`dev-docs/endpoints/`・`dev-docs/issues/` を作った理由、レビューの進め方(1グループずつ)を明文化。

6. **`dev-docs/talks/` の新設**
   - 実装前の設計レビューでの決定事項・経緯を残す場所として新設。`dev-docs/endpoints/`・`dev-docs/issues/`(結論としての仕様)と役割を分け、「なぜそう決めたか」をここに書く。
   - `CLAUDE.md` に「定期的に見直して更新する」ことと、更新タイミングの目安を明記。

7. **レビューで確定した仕様(デプロイ・起動設定関連)**
   - デプロイ削除: 事前に [スケーリング](../issues/deploys/003-post-deploy-deployid-scale.md) で `replicas` を 0 にする手順は不要。稼働中の deploy に対してもそのまま削除コマンドを受け付け、削除処理の内部でコンテナ停止まで行う。
   - apply系(起動設定など)の処理順序を明確化: `pending_*` の値を使って**先に実際のインフラへの反映を試み、結果(成功/失敗)が確定してから**正式な値を `pending_*` の内容で上書きする。この順序は今後作る service/ingress/volume の apply でも統一する方針を `CLAUDE.md` に明記した。

8. **レビューで確定した仕様(サービス関連)**
   - デプロイ関連で確立した apply の処理順序(pendingで先に反映→結果確定後に正式値更新)をそのまま適用。新たな方針転換はなし。

9. **レビューで確定した仕様(イングレス関連)**
   - イングレス作成数の上限は設けない(1プロジェクトにつき無制限に作成可能)。
   - イングレス削除: `status` が `"applying"` の間は 409 で拒否する(進行中のapplyと排他制御する。デプロイ削除とは異なり、ここでは排他制御を優先)。
   - イングレス適用: `pending_rules` の `serviceId`/`port` の妥当性(同一project内か、該当port存在、protocolが`"tcp"`か)を、[イングレス更新](../issues/ingresses/005-put-projects-projectid-ingresses-ingressid.md) 時点だけでなく apply 実行時にも再検証する。更新から適用までの間に service 側のポート構成が変わる可能性があるため。

10. **レビューで確定した仕様(ボリューム関連)**
    - 当初「リサイズ廃止・名前変更のみ即時反映」で一度確定したが、その後方針転換。最終的に以下で確定:
      - `sizeMB` にアカウントごとの上限(デフォルト 5GB = 5120MB)を設け、デフォルト超過は申請で引き上げる想定(申請API自体は別途アカウント管理グループのスコープとし、今回は作らない)。
      - ボリュームの拡張(リサイズ)は復活。ただし拡大のみ許可(縮小不可)。
      - `name` 変更と `sizeMB` 拡張はエンドポイントを分離: 名前変更(`PATCH /volumes/:volumeId`)は即時反映、拡張(`PATCH /volumes/:volumeId/size` → apply/discard)はpending_*→apply/discardモデルで、他グループと同じ処理順序(pendingで先にストレージへの反映を試みる→結果確定後に正式値を更新)を踏襲する。
    - デプロイ側のボリュームマウント適用は、他のconfig/serviceのapplyと同様に deployment のコンテナ再起動を伴うことを確認(既存仕様通り、変更なし)。
