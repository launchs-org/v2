API と自動デプロイ

画面でできることは、API からも、できます。CI やスクリプトから操作したり、新しいイメージを作ったときに、自動で入れ替えたりできます。

はじめかた(3 ステップ)

  1. トークンを作る — アカウント設定(または、プロジェクトの設定)のAPI トークンで、トークンを発行を押します。トークンは、発行したときの 1 度しか表示されません。保存してください。
  2. 呼んでみる — Authorization: Bearer <トークン> を付けて、API を呼びます。
  3. 要らなくなったら失効 — 一覧の失効で、すぐに使えなくなります。
curl -H "Authorization: Bearer lkt_…" https://<このサービスのホスト>/api/v1/projects

認証: 2 種類のトークン

API トークン(lkt_…)ログインのトークン
使う場面機械(CI、スクリプト)画面(ブラウザ)
有効期間発行のときに決める(30 日・90 日・1 年・無期限)15 分(更新しながら使う)

API トークンの権限

権限できること
読み取り専用見るだけ(GET)。状態の監視向け
全ての操作作成・更新・削除も、あなたと同じ。ただし、API トークンの管理は、できません(トークンが、別のトークンを作れないように)
イメージの更新だけ1 つの deploy の、イメージの更新と、自動デプロイ(webhook)だけ。deploy の画面で発行します
対象を絞る

プロジェクトの設定で発行したトークンは、そのプロジェクトだけを操作できます。CI には、必要なものだけに絞ったトークンを渡してください。絞ったトークンでは、プロジェクトの外の操作(GET /projects の一覧や、POST /deploy での作成)は、まだできません。

トークンは、パスワードと同じ

リポジトリに書いたり、チャットに貼ったりしないでください。CI の「シークレット」に入れます。漏れたかもしれないときは、すぐ失効します。

基本のルール

  • URL は /api/v1/…。本文は JSON(Content-Type: application/json)。
  • エラーは {"error": {"code": "not_found", "message": "…"}} の形。主な code は、invalid_request(400)、unauthorized(401)、forbidden(403)、not_found(404)、conflict(409。反映中など)。
  • 一覧は limit(最大 100)と cursor(前回の nextCursor)で、ページをめくります。
  • 変更は「保存 → 反映」の 2 段階です。PUT …/config のような変更は、まず反映待ちとして保存され、POST …/apply で、はじめて実際に反映されます(POST …/discard で破棄)。反映は非同期で、すぐに応答します。結果は、deploy の status(applying → active か failed)を、GET /deploy/:deployId で確かめます。
  • 反映中(applying)の deploy への変更は、409 になります。少し待って、やり直してください。

自動デプロイ(webhook)

新しいイメージを作ったときに、CI から 1 回呼ぶだけで、deploy のイメージを入れ替えて、反映します。

  1. deploy の概要にある自動デプロイ(webhook)で、トークンを発行を押します。(この deploy の、イメージの更新だけができるトークンです)
  2. CI のシークレットに、トークンを入れます。
  3. イメージを push したあと、次を呼びます。
curl -X POST https://<このサービスのホスト>/hooks/deploy \
  -H "X-Launchs-Token: $LAUNCHS_TOKEN" \
  -d '{"tag":"v2"}'
本文意味
{"tag":"v2"}いまのイメージの、タグだけを差し替える(ghcr.io/org/app:v1 → …:v2)
{"imageRef":"ghcr.io/org/app:v2"}イメージを、まるごと指定する
Docker Hub の webhook の形式そのまま使えます(push_data.tag)
  • 応答は {"changed": true, "applied": true}。同じイメージなら、何も起きません(changed: false)。CI が、何度呼んでも安全です。
  • 反映中は 409 です。少し待って、もう一度呼んでください。
  • 反映に失敗したら、元のイメージのままで、動き続けます。
  • タグに latest だけを使うと、「変わった」と判断できません。コミットの ID など、毎回違うタグを付けてください。

GitHub Actions の例

deploy の自動デプロイ(webhook)のGitHub Actions で自動デプロイを押すと、3 つの手順で案内されます。

  1. YAML を作る — 対象のブランチ、ビルドするフォルダ、ビルドの方法(Railpack=Dockerfile なし、または Dockerfile)を選ぶと、YAML ができます。ダウンロードして、リポジトリの .github/workflows/ に置き、push します。どのリポジトリに置いても動きます。
  2. Secrets を登録 — GitHub の Settings → Secrets and variables → Actions に、LAUNCHS_URL と LAUNCHS_TOKEN を登録します(値は、画面からコピーできます)。
  3. ghcr を公開 — 最初の実行のあと、パッケージを Public にします。
トークンは、YAML ではなく、Secrets に入れます。発行済みのトークンは、トークンを表示で、もう一度見られます。

ghcr.io を使うとき

GitHub のパッケージは、最初は非公開です。launchs は、非公開のイメージを取得できないので、GitHub の Packages の設定で、公開(Public)にしてください。

- name: launchs に反映
  run: |
    curl -fsS -X POST "${{ secrets.LAUNCHS_URL }}/hooks/deploy" \
      -H "X-Launchs-Token: ${{ secrets.LAUNCHS_TOKEN }}" \
      -d "{\"tag\":\"${{ github.sha }}\"}"
